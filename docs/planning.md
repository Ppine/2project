# 2장프 서비스 기획안 — 돈구마

> 최종 수정: 2026-10-28

> 확장 검토 문서 추가: 2026-10-29 — [안드로이드 자동 해지 구현 방안](auto-cancellation.md). 아래 기본 기획과 별도로 검토하며, 도입 시 읽기 전용 권한·화면 데이터 처리 원칙을 함께 개정한다.

## 개요

사용자의 결제 내역을 분석해 **어디로 새는지 모르는 돈**을 찾아주는 서비스다. 사람이 앱으로 쓰는 것뿐 아니라, AI 에이전트가 사용자를 대신해 호출하는 도구(MCP/API)로 동작하는 것이 핵심이다.

**문제 정의**

- 구독 서비스가 늘면서 내가 무엇을 얼마에 구독 중인지 한눈에 파악하기 어렵다.
- 무료 체험 후 자동 전환, 잊어버린 연간 결제처럼 모르는 사이 빠져나가는 돈이 있다.
- 카드 명세서에 실제 가맹점 대신 결제대행사(PG사) 이름만 찍혀 어떤 지출인지 알 수 없는 경우가 많다. 예: `토스페이먼츠`, `KG이니시스`, `NICE페이`, `PAYPAL *`.
- 앱스토어·플레이스토어의 구독 관리 화면은 그 마켓의 인앱결제로 산 구독만 보여준다. 웹에서 카드로 직접 결제한 구독이나 외부 결제로 산 구독은 빠진다. 구독이 여러 결제 경로에 흩어져 있어 전체를 한 번에 볼 곳이 없다.
- 앱마켓 결제는 카드 명세서에 `APPLE.COM/BILL`, `GOOGLE*` 같은 한 줄로만 찍혀, 어떤 앱 구독인지 알 수 없다. PG사 표기와 같은 문제다.

## 목표와 타깃 사용자

목표는 세 가지다.

1. 사용자가 구독 중인 서비스와 월·연 금액을 자동으로 파악한다.
2. 출처가 불분명한 결제(PG사 표기)가 실제로 어떤 지출인지 추정해 준다.
3. 새로 생긴 자동결제, 금액 인상, 중복 구독처럼 새는 돈을 알려준다.

| 사용자 | 누구인가 | 원하는 것 |
| --- | --- | --- |
| 사람 | 구독을 여러 개 쓰는 20~30대, 자취생·직장인 | "내 돈 어디로 갔지?"에 대한 빠른 답 |
| AI 에이전트 | Claude, ChatGPT 같은 개인 비서형 에이전트 | 사용자 대신 지출을 조회·분석할 수 있는 구조화된 도구 |

## 핵심 기능

기능은 구독 탐지, 불분명 결제 출처 추적, 새는 돈 알림의 세 축이다.

| 기능 | 하는 일 | 판단 근거 | 우선순위 |
| --- | --- | --- | --- |
| 구독 탐지 | 반복 결제를 묶어 서비스명·금액·주기·다음 결제일 목록을 만든다 | 같은 가맹점, 비슷한 금액, 일정한 간격(월/연) | MVP |
| 불분명 결제 출처 추적 | PG사·모호한 가맹점명을 실제 서비스 후보로 바꾼다 | 가맹점 표기 사전, 금액 패턴(예: 알려진 구독료와 일치), 결제 시각, 영수증 메일, LLM 추론 | MVP |
| 새는 돈 알림 | 사용자가 놀라야 할 변화를 짚어준다 | 무료체험 후 처음 결제, 금액 인상, 중복 구독(예: 음원 스트리밍 2개), 한동안 안 쓴 구독 | 2차 |
| 해지 가이드 | 구독별 해지 방법·링크를 안내한다 | 서비스별 해지 경로 DB | 2차 |

출처 추적은 단정이 아니라 **후보 + 신뢰도**로 보여준다. 사용자가 확인해 준 매핑은 사전에 반영해 정확도를 올린다.

## 서비스 구조: AI 에이전트가 사용자

에이전트는 MCP 서버로, 사람은 웹 대시보드로 같은 분석 엔진을 쓴다. 에이전트가 주 사용자이므로 도구 응답은 사람이 아니라 에이전트가 읽기 좋은 구조화된 JSON(서비스명, 금액, 주기, 신뢰도, 근거)으로 설계한다.

```
사용자 ──> AI 에이전트 (Claude, ChatGPT 등) ──> MCP 서버 ─┐
   └────> 웹 대시보드 ─────────────────────> REST API ─┤
                                                          v
                 분석 엔진: 1. 정규화·정제 → 2. 반복 결제 탐지 → 3. 출처 추론
                     │                                       │
                     v                                       v
     DB (거래 내역, 가맹점/PG사 사전, 사용자 확인 매핑)    외부 LLM API
```

| MCP 도구 (예시) | 역할 |
| --- | --- |
| `list_subscriptions` | 구독 목록 |
| `explain_charge` | 결제 출처 추적 |
| `find_leaks` | 새는 돈 찾기 |

도구 이름은 예시이며, 기능 확정 후 인터페이스를 정한다.

## 데이터 수집과 분석 파이프라인

마이데이터는 우리 팀이 쓸 수 없으므로, 직접 만든 데모 데이터로 개발하고 시연한다. 데모 데이터는 실제 카드사 명세서와 같은 포맷으로 만들어, 나중에 실제 파일을 올려도 그대로 처리되게 한다.

| 수집 방식 | 장점 | 한계 | 단계 |
| --- | --- | --- | --- |
| 데모 데이터 (직접 제작) | 개인정보 걱정 없이 원하는 상황(구독, PG사 결제, 무료체험 전환)을 마음대로 만들 수 있다 | 실제 데이터만큼 다양하지 않다 | MVP 기본 |
| 카드사 명세서 업로드 (Excel/CSV/PDF) | 인허가 없이 바로 가능하다 | 카드사마다 포맷이 다르다. 자동 갱신이 안 된다 | MVP (데모와 같은 포맷) |
| 결제 알림 문자·앱 푸시 복사/공유 | 거의 실시간이다. 안드로이드는 알림 접근 권한으로 자동 수집이 가능하다 | 아이폰은 자동 수집이 안 되고(수동 공유만), 포맷이 제각각이다 | 2차 |
| 영수증 이메일 (Gmail 연동) | PG사 결제의 실제 서비스명을 밝힐 단서가 된다 | OAuth 권한, 개인정보 부담이 크다 | 2차 |
| 마이데이터 / 금융 API | 자동 수집, 표준 포맷 | 우리 팀은 사용할 수 없다 | 제외 |

데모 데이터에는 최소한 다음 상황을 넣는다.

- 여러 구독이 섞인 월별 결제 (OTT, 음원, 클라우드, AI 서비스 등)
- 실제 서비스명 대신 PG사 이름(`토스페이먼츠`, `KG이니시스`, `NICE페이` 등)이나 `APPLE.COM/BILL`, `GOOGLE*` 같은 앱마켓 묶음 표기로 찍힌 결제
- 무료체험 후 처음 결제, 중간에 금액이 오른 구독, 겹치는 구독
- 반복 결제가 아닌 일반 소비 (탐지에서 걸러져야 하는 노이즈)
- 정답 라벨: 각 결제의 실제 서비스명과 구독 여부 (정확도 측정용)

**안드로이드 결제 알림 자동 수집 (2차)**

안드로이드에서는 사용자가 허용하면 카드사 앱의 결제 알림을 자동으로 읽을 수 있다. 아이폰에는 같은 기능이 없다.

- **알림 읽기**: `NotificationListenerService`를 쓰면 다른 앱 알림의 패키지명, 제목, 본문, 시각을 읽는다. 사용자가 설정의 "알림 접근 허용"에서 직접 켜야 한다.
- **문자 직접 읽기는 어렵다**: `READ_SMS`는 구글 플레이 정책상 기본 문자 앱이 아니면 거의 승인되지 않는다. 알림 접근이 현실적인 대안이다.
- **플레이스토어 심사**: 알림 접근도 민감 권한이라 출시 때 사용 사유를 설명해야 한다. 정책은 바뀔 수 있으니 출시 전에 다시 확인한다.
- **다른 앱 알림이 켜져 있는지는 직접 알 수 없다**: 공개 API는 내 앱의 알림 상태만 알려준다. 다른 앱 상태를 알려면 시스템 권한이 필요하다.
- **대신 간접적으로 추정한다**: 카드사 앱 알림이 들어오면 켜진 것이다. 오래 안 들어오면 "OO카드 알림이 30일째 없어요, 알림이 꺼져 있지 않은지 확인해 주세요"처럼 안내만 한다. 결제가 없었을 수도 있어 꺼졌다고 단정하지는 않는다.
- **설정 화면 안내**: `Settings.ACTION_APP_NOTIFICATION_SETTINGS`에 카드사 앱 패키지명을 넣어 그 앱의 알림 설정 화면으로 바로 보낼 수 있다. 켜는 것은 사용자가 한다.
- **앱 설치 확인 제한**: 안드로이드 11부터는 다른 앱 설치 여부 확인도 제한되므로, 확인할 카드사 앱을 매니페스트에 미리 선언한다.

온보딩 흐름: 사용 중인 카드사 선택 → 알림 접근 허용 → 카드사 앱 알림 설정 화면 안내 → 실제 알림 수신으로 정상 동작 확인. 앱 개발까지 하면 범위가 커지므로 2차 단계로 둔다.

분석은 다섯 단계로 흐른다.

1. **정규화**: 카드사별 포맷을 날짜·가맹점명·금액·통화·승인번호의 공통 스키마로 바꾼다.
2. **가맹점명 정제**: `GOOGLE*YOUTUBE`, `토스페이먼츠(주)` 같은 표기를 규칙과 사전으로 정리한다.
3. **반복 결제 탐지**: 가맹점·금액·간격으로 묶어 구독 후보를 만든다.
4. **출처 추론**: 사전에 없는 건은 LLM이 금액·날짜·PG사·다른 거래 맥락을 보고 후보와 신뢰도를 낸다.
5. **사용자 피드백**: 확인·수정한 결과를 사전에 저장한다.

## 사용자 시나리오

**시나리오 1. 구독 점검**

사용자가 에이전트에게 "나 지금 뭐 구독하고 있어?"라고 묻는다. 에이전트는 서비스의 구독 목록 도구를 호출해 서비스별 월 금액과 합계, 다음 결제일을 답한다.

**시나리오 2. 정체 불명 결제**

명세서에 `토스페이먼츠 14,900원`이 매달 찍힌다. 에이전트가 출처 추적 도구를 호출하면 서비스는 "금액과 주기가 OO 구독료와 일치, 신뢰도 높음" 같은 후보를 돌려준다. 사용자가 맞다고 하면 그 매핑을 저장한다.

**시나리오 3. 새는 돈 알림**

무료체험이 끝난 서비스가 처음 결제됐다. 에이전트가 주간 점검 때 이를 발견하고 "새 자동결제가 생겼는데 계속 쓸 건가요?"라고 사용자에게 묻는다.

## 보안·개인정보·법적 고려사항

결제 내역은 민감한 금융 정보다. 그래서 저장을 최소화하고, 에이전트에게도 필요한 만큼만 내준다.

- **저장하지 않는 것**: 카드번호, 계좌번호, 금융사 로그인 정보. 업로드 파일에서 파싱 단계에 마스킹한다.
- **저장하는 것**: 날짜, 가맹점명, 금액, 분류 결과. 암호화해 두고, 사용자가 언제든 전체 삭제할 수 있게 한다.
- **에이전트 권한**: 에이전트는 사용자가 발급한 토큰으로만 접근한다. 기본은 읽기 전용이고, 해지처럼 돈이 움직이는 행동은 하지 않는다.
- **LLM 전송**: 출처 추론 때 외부 LLM에 보내는 데이터는 가맹점명·금액·날짜로 한정하고, 이를 사용자에게 고지한다.
- **법적 확인 필요**: 개인정보 보호법상 동의 범위, 마이데이터(본인신용정보관리업) 규제에 해당하는지는 실제 서비스로 확장하기 전에 확인해야 한다. 학기 프로젝트는 마이데이터를 쓰지 않고 데모 데이터로 진행하므로 실제 개인정보를 다루지 않는다.

## MVP 범위, 리스크, 열린 질문

MVP는 "명세서 업로드 → 구독 목록 + 불분명 결제 후보 → MCP로 에이전트가 조회"까지다.

**MVP에 넣는 것**

- 데모 데이터 세트(카드사 1~2곳 포맷, 정답 라벨 포함) + 명세서 파서
- 가맹점명 정제 규칙 + PG사/구독 서비스 사전 (초기 수작업)
- 반복 결제 탐지, LLM 기반 출처 추론
- MCP 서버 (읽기 도구 3~4개) + 간단한 웹 대시보드

**나중으로 미루는 것**: 이메일 연동, 자동 알림, 해지 가이드.

| 리스크 | 대응 |
| --- | --- |
| PG사 표기만으로는 출처를 못 찾는 경우가 많다 | 후보 + 신뢰도로 보여주고, 사용자 피드백으로 사전을 키운다 |
| 카드사마다 명세서 포맷이 다르다 | 파서를 플러그인 구조로 만들고 MVP는 1~2곳만 지원한다 |
| 데모 데이터가 실제와 달라 실제 명세서에서는 탐지가 잘 안 맞을 수 있다 | 실제 명세서 포맷과 PG사 표기를 참고해 만들고, 가능하면 팀원 명세서 일부(마스킹)로 검증한다 |
