# 추가 개선 사항

> 작성 2026-11-09 · Gemini 교체(#12)와 출처 추론 규칙 수정(#13) 이후 다음 단계

## 배경

이번에 바뀐 것:

- 출처 추론 LLM 을 Claude 에서 **Gemini(무료 등급)** 로 바꿨다. 호출 타임아웃은 20초이고, 성공한 결과는 서버 메모리에 캐시한다.
- 업로드 형식을 넓혔다: 카드 CSV, **카드+계좌이체 CSV**, **은행·카드앱 캡처 이미지**(Gemini 가 읽음).
- 형식별 시연 파일 8개를 [data/samples](../data/samples/README.md)에 추가했다.
- 금액만 같으면 서비스로 확정하던 규칙을 고쳤다. 이제 금액 일치는 PG사·앱마켓 결제에서만 확정 근거로 쓴다. 한글 가맹점 표기도 인식한다.

이 문서는 그 과정에서 확인했지만 아직 고치지 않은 것을 모은 것이다. 모든 항목은 실제로 돌려 보고 확인한 근거가 있다.

**우선순위**

| 단계 | 기준 |
| --- | --- |
| P0 | 시연에서 실패하거나, 개인정보 원칙과 어긋나는 것 |
| P1 | 분석 결과가 틀리게 보이는 것, README 핵심 기능 중 빠진 것 |
| P2 | 운영·확장을 편하게 하는 것 |

**작업 크기**: S(반나절 이내) · M(1~2일) · L(3일 이상)

## P0: 시연 전에

### 1. Gemini 무료 한도(하루 20회) 대응 — M

- **문제**: 테스트 중 `429 Rate limit exceeded (limit: 20 requests per day on Free Tier)`가 났다. 이미지 1장, 처음 보는 반복 결제 1건이 각각 1회를 쓴다. 3a·3b 파일만 올려도 8회쯤 쓴다. 한도를 넘으면 이미지 업로드는 실패하고, 출처 추론은 규칙 기반 결과로만 나온다.
- **제안**
  - 추론 결과를 DB 에 저장해 서버를 다시 켜도 남게 한다. 지금은 메모리 캐시라 재시작하면 사라진다(`GeminiInferer._cache`, `backend/analysis/llm.py`).
  - 캐시 키에서 결제일 목록(`dates`)을 뺀다. 지금은 새 달 명세서가 들어오면 같은 구독도 다시 묻는다.
  - 429 를 받으면 화면에 "AI 사용 한도를 넘었어요"라고 알린다. 지금은 로그에만 남는다.
- **관련 파일**: `backend/analysis/llm.py`, `backend/ledger/models.py`

### 2. 대시보드를 열 때마다 LLM 을 부르지 않기 — M

- **문제**: `_analysis()`(`backend/ledger/api.py`)가 대시보드 조회(GET)마다 `analyze()` → `identify()`를 거쳐, 규칙으로 못 푼 반복 결제마다 Gemini 를 동기로 부른다. 3번 샘플은 처음 한 번 여는 데 13~45초 걸렸다. 1번 항목의 한도도 이 때문에 빨리 닳는다.
- **제안**: 명세서를 올릴 때 한 번만 추론해 결과를 저장하고, 조회 때는 저장된 결과만 쓴다. 사용자가 후보를 고르면(`MerchantAlias`) 그 값이 우선한다.
- **관련 파일**: `backend/ledger/api.py`, `backend/analysis/infer.py`

### 3. 이미지 업로드 개인정보 고지 — S

- **문제**: 캡처 이미지는 통째로 Google 로 보내진다. 잔액이나 계좌번호도 함께 넘어간다. README 개인정보 원칙에는 이 예외를 적었지만, 화면에는 안내가 없다.
- **제안**: 업로드 버튼(`UploadButton`, `frontend/src/App.jsx`)에서 이미지를 고르면 "이미지 전체가 Google Gemini 로 전송됩니다" 안내와 확인을 거친다. 같은 내용을 [planning.md 보안·개인정보](planning.md#보안개인정보법적-고려사항) 절에도 반영한다.

### 4. 기본 모델과 폴백 — S

- **문제**: 기본값 `gemini-3.8-flash`(`DEFAULT_MODEL`)는 테스트 당일 504·타임아웃이 났다. `gemini-3.5-flash`는 정상이었다. 지금은 각자 `.env` 에 `GEMINI_MODEL` 을 넣어야 한다.
- **제안**: 기본값을 응답이 확인된 모델로 바꾼다. 또는 실패하면 다음 모델로 넘어가는 목록을 둔다. 폴백을 두면 1번의 한도는 모델마다 따로 계산되는지 확인한다.
- **관련 파일**: `backend/analysis/llm.py`, `.env.example`

## P1: 다음 스프린트

### 5. 고정비와 구독 분리 — M

- **문제**: 월세·통신비·보험·정기후원 같은 이체 고정비가 구독으로 잡혀 합계에 들어간다. 3a 샘플은 월 608,230원(월세 450,000원 포함)으로 나온다. 카드+계좌이체 CSV 의 `구분` 열(카드결제·계좌이체·자동이체)은 파서가 읽지 않고 버린다(`FORMATS`, `backend/analysis/parsers.py`).
- **제안**
  - 결제 유형을 저장한다. 결제 유형은 계좌번호가 아니라서 개인정보 원칙에 걸리지 않는다.
  - 이체로 반복되는 결제는 '고정 지출'로 따로 보여 주고, 구독 합계에서 뺀다.
  - 사용자가 행마다 구독인지 고정비인지 바꿀 수 있게 한다.

### 6. 이미지 판독 결과 확인 단계 — M

- **문제**: Gemini 가 읽은 거래가 확인 없이 바로 저장된다. 날짜·금액을 잘못 읽으면 그대로 분석에 들어간다. 이미지에는 승인번호가 없어 중복 판단이 (날짜·가맹점·금액)에만 기대고 있다.
- **제안**: 읽은 결과를 표로 먼저 보여 주고, 사용자가 고치거나 줄을 지운 뒤 저장한다.

### 7. 새는 돈 알림 나머지 — M

- **문제**: 지금 알림은 금액 변경·해지 후 결제·결제 확인 안 됨·출처 확인 4종뿐이다(`build_alerts`, `backend/analysis/infer.py`). README 의 '새는 돈 알림' 중 두 가지가 빠져 있다.
  - **중복 구독**: 2a 샘플은 YouTube Premium 을 두 카드로 결제한다(`GOOGLE*YOUTUBE` + `APPLE.COM/BILL` 14,900원). 1b 는 Apple Music 과 Spotify 를 함께 결제한다.
  - **무료체험 후 첫 결제**: 1a 의 CLASS101+ 가 7월에 처음 결제된다.
- **제안**: 같은 서비스(또는 같은 분류: 음원, OTT 등)가 동시에 활성이면 중복 알림을 띄운다. 명세서 기간 중간에 처음 나타난 구독은 "새로 시작된 구독" 알림을 띄운다. 분류가 필요하면 구독료 표에 분류 열을 추가한다.

### 8. 연 1회 결제 탐지 — S

- **문제**: 반복 결제는 2회 이상부터 잡는다(`MIN_CHARGES = 2`, `backend/analysis/detect.py`). 그래서 2b 의 Duolingo 연간 129,000원처럼 명세서 기간에 한 번만 찍힌 연간 구독은 보이지 않는다.
- **제안**: 금액이 구독료 표의 **연간 요금**과 정확히 같고 PG사·앱마켓 결제이면, 목록이 아니라 "연간 구독일 수 있어요" 알림으로 보여 준다.

### 9. PG사 결제의 금액 변경 추정 — S

- **문제**: PG사·앱마켓 표기는 여러 서비스가 섞일 수 있어 금액 변경을 일부러 합치지 않는다(`_merge_price_changes`). 그래서 `NICE페이` 9,900→13,900원 변경이 구독 2건으로 보이고, 옛 금액 쪽에 '해지 의심' 오탐이 붙는다(샘플을 만들 때 실제로 확인).
- **제안**: 같은 PG 의 한 금액 구간이 끝난 바로 다음 주기에 다른 금액 구간이 시작하면, 합치지는 않고 "금액이 바뀐 같은 구독일 수 있어요"로 묶어 보여 준다. 사용자가 확인하면 합친다.
