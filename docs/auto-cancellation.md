# 안드로이드 자동 해지 구현 검토안

> 작성일: 2026-10-29
> 상태: 구현 전 검토안. 공식 문서에서 확인한 내용과 팀을 위한 설계 제안을 구분한다.
> 관련 문서: [전체 서비스 기획안](planning.md)

## 1. 목표와 권장 방향

사용자가 불필요한 구독을 선택하면 에이전트가 안드로이드 기기에서 해지 절차를 진행한다. 기존의 구독 탐지·결제 출처 추적에 이어 실제 구독 정리까지 돕는 확장 기능이다.

첫 목표는 **지원 서비스 1~2개에서 해지 확인 화면까지 자동 이동**하는 것이다. 다음 단계에서 사용자의 실행 승인 후 해지 완료와 갱신 중단 상태까지 확인한다. 모든 앱을 다루는 범용 에이전트보다 서비스별로 검증한 절차부터 구현한다.

권장 순서는 **PC 연결 방식으로 검증 → 서비스별 절차 정리 → 폰에서 독립 실행하는 앱 검토**다. 현재 구현되거나 지원이 확정된 기능은 아니다.

기본적인 ‘해지’는 다음 결제의 자동 갱신을 중단하는 뜻으로 사용한다. 즉시 이용 종료, 환불, 계정 탈퇴는 효과가 다르므로 별도 행동으로 구분한다.

## 2. 딥링크와 화면 조작

딥링크는 앱의 특정 화면으로 들어가는 링크다. ‘앱 실행 → 설정 → 구독 관리’ 대신 관리 화면으로 바로 이동할 수 있다. 링크를 여는 것만으로 해지가 완료되지는 않는다.

| 기술 | 역할 | 한계 |
| --- | --- | --- |
| 공식 관리 URL·딥링크 | 구독 관리 또는 해지 화면 진입 | 로그인과 이후 조작이 필요할 수 있다 |
| UI Automator | 테스트 기기의 화면 요소 탐색, 클릭, 입력, 스크롤 | 테스트 실행 환경이 필요하다 |
| AccessibilityService | 권한을 허용한 폰에서 화면 읽기와 조작 | OS·앱의 접근 제한 및 Play 배포 정책 확인이 필요하다 |
| 이미지 인식·OCR | 화면 요소 정보가 부족할 때 해석 보조 | 캡처 제한, 인식 오류, 화면 전송 문제가 있다 |
| 리버스 엔지니어링 | 딥링크·화면 경로·동작 구조 조사 | 발견한 경로의 외부 실행이나 서버 권한을 보장하지 않는다 |

실행 우선순위는 **공식 링크 → 검증된 외부 진입 경로 → 서비스별 화면 조작**으로 제안한다. 고정 좌표보다 요소의 ID·텍스트·설명과 현재 화면 상태를 함께 확인하는 방식을 우선한다.

Google Play 구독 관리 링크 예시:

```text
구독 목록:
https://play.google.com/store/account/subscriptions

특정 구독 관리:
https://play.google.com/store/account/subscriptions?sku=PRODUCT_ID&package=PACKAGE_NAME
```

특정 구독 링크에는 실제 패키지명과 상품 ID가 필요하다. 카드 내역만으로 상품 ID를 알 수 있다고 가정하지 않는다. 링크를 연 계정에서 실제 구독이 보이는지 확인한다. 웹 직접 결제나 통신사·제휴 결제는 해당 결제 경로의 관리 페이지를 이용한다.

공식 근거: [Google Play 구독 관리 링크](https://developer.android.com/google/play/billing/subscriptions), [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator), [접근성 서비스](https://developer.android.com/guide/topics/ui/accessibility/service).

## 3. 구현 방식 비교

### A. PC 연결 방식 — 첫 시연에 권장

```text
사용자 → AI 에이전트 → MCP 서버 → 로컬 기기 실행기
                                      ↓
                              ADB + UI Automator
                                      ↓
                              안드로이드 테스트 폰
```

- PC에서 분석·요청 처리를 실행하고, 기기 실행기가 화면을 관찰하며 정해진 절차를 수행한다.
- 실기기는 USB 디버깅을 켜고 연결할 PC를 기기에서 승인해야 한다. 무선 디버깅도 지원 조건에 따라 사용할 수 있다.
- 초기에는 로그인된 테스트 계정과 화면 잠금이 해제된 기기를 사용한다.
- 기본적인 UI 테스트를 위해 루팅을 전제로 하지 않는다.
- PC 연결과 테스트 실행 환경이 필요하므로 일반 사용자가 설치하는 앱의 배포 구조와는 다르다.
- AI가 화면을 보고 다음 행동을 정하는 실험은 이 개발 환경에서 검증할 수 있으나, 이것이 Play 배포 가능성을 입증하지는 않는다.

공식 근거: [ADB 연결·인증](https://developer.android.com/tools/adb), [UI Automator의 앱 간 테스트](https://developer.android.com/training/testing/other-components/ui-automator).

### B. 폰에서 독립 실행하는 앱 — 후속 검토

안드로이드 보조 앱에 접근성 서비스를 두고 사용자가 설정에서 권한을 켜면 화면 요소를 읽고 클릭·스크롤·뒤로 가기를 수행한다. 제스처와 캡처에는 각각 필요한 기능 선언과 지원 OS 조건을 확인한다.

캡처가 차단된 화면, 요소 정보가 부족한 화면, 로그인·추가 인증이 필요한 화면에서는 자동 진행을 멈추고 사용자에게 넘긴다. 잠긴 기기를 자동 해제하거나 보안 제한을 우회하는 방식은 구현 범위에 포함하지 않는다.

**2026-10-29 확인한 Google Play 정책:** 접근성 API를 이용해 앱이 자율적으로 행동을 시작하고 계획·실행하는 사용은 금지한다. 사람이 미리 정의한 정적인 규칙에 따른 자동화는 이 금지와 구분한다. 장애인 지원 도구에 대한 예외를 일반 구독 관리 앱에 그대로 적용할 수는 없다.

따라서 배포용 설계는 AI가 요청을 해석하고 실제 화면 조작은 서비스별 고정 절차가 담당하는 방향으로 검토한다. 이는 정책 문구에 근거한 제안이며 심사 통과를 보장하지 않는다. **마지막 사용자 승인만 추가한다고 자율형 AI 조작이 허용되는 것은 아니다.** 접근성 사용 고지·동의·신고 요건과 출시 시점 정책도 다시 확인한다. APK 직접 설치도 기기의 권한·보안 제한을 없애 주지 않는다.

공식 근거: [Google Play 접근성 API 자동화 정책](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en), [접근성 API 기능·캡처 제약](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService).

## 4. 리버스 엔지니어링 활용

공개 문서와 화면에서 경로를 찾기 어려울 때 서비스별 조사 수단으로 활용한다. 딥링크 자체는 리버스 엔지니어링이 아니며, APK 분석으로 비공개 링크를 찾는 과정이 리버스 엔지니어링에 해당한다.

| 조사 방법 | 조사 내용 | 결과 활용 |
| --- | --- | --- |
| JADX 정적 분석 | 매니페스트, URL 문자열, 구독 관리 관련 코드·리소스 | 진입 링크와 화면 전환 경로 후보 확보 |
| 실제 화면 관찰 | 메뉴, 버튼, 로그인 상태에 따른 분기 | 서비스별 조작 절차 작성 |
| Frida 동적 분석 | 버튼 실행 시 함수 호출과 런타임 동작 | 정적 분석 결과와 실제 동작 비교 |

JADX는 APK·DEX와 매니페스트·리소스를 분석하는 도구다. Frida는 실행 중인 앱을 관찰하는 도구이며, 사용 방식에 따라 루팅이나 앱 재패키징 등이 필요할 수 있다. 일반 사용자 기능에 루팅을 요구하는 구조는 초기안에서 제외한다.

조사는 팀이 관리하는 기기와 테스트 계정에서 수행하고 대상 서비스의 이용 조건과 분석 허용 범위를 확인한다. 발견한 링크는 외부 호출과 로그인 상태를 별도로 검증한다. 내부 화면이 `exported=false`이거나 별도 권한이 필요하면 이름을 알아도 일반 앱에서 바로 열 수 없다.

내부 해지 API를 직접 호출하는 방식도 조사 후보지만 초기 구현 경로로 채택하지 않는다. 엔드포인트를 안다고 인증·인가가 생기는 것은 아니며 세션·추가 인증·서버 검증과 서비스 변경에 의존하기 때문이다. 우선 분석 결과로 정상적인 진입 경로를 찾고 로그인된 화면에서 절차를 수행한다.

Google Play에도 구독 취소 API가 있지만 해당 앱에 대한 Play Console 권한과 구매 토큰 등이 필요하다. 일반 소비자의 Google 로그인만으로 모든 타사 구독을 취소할 수 있는 API로 취급하지 않는다.

근거: [JADX](https://github.com/skylot/jadx), [Frida Android](https://frida.re/docs/android/), [Activity 외부 실행 조건](https://developer.android.com/guide/topics/manifest/activity-element), [Google Play API 권한](https://developers.google.com/android-publisher/getting_started), [구독 취소 API](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptionsv2/cancel).

## 5. 사용자 흐름과 실행 조건 제안

1. **대상 선택:** 사용자가 해지할 항목을 고른다. 결제 출처 추론의 후보만으로 대상을 확정하지 않는다.
2. **결제 경로 확인:** Google Play, 서비스 웹사이트, 통신사·제휴 결제 중 실제 관리 주체를 확인한다.
3. **관리 화면 진입:** 링크나 검증된 절차로 진입한다. 로그인은 사용자가 기기에서 직접 수행한다.
4. **실제 구독 대조:** 계정, 서비스, 요금제, 갱신 상태를 확인한다. 잘못된 계정이거나 여러 항목 중 특정할 수 없으면 사용자에게 선택을 요청한다.
5. **해지 확인 화면 도달:** 서비스별 절차로 이동한다. 정해진 분기에 없는 화면이나 혜택 변경 제안은 임의로 선택하지 않는다.
6. **효과 확인과 승인:** 자동 갱신 중단인지 즉시 이용 종료인지, 표시된 이용 종료일과 혜택 소멸 내용을 보여준다. 확인할 수 없는 값은 추정하지 않는다.
7. **실행·검증:** 해당 작업에 대한 승인을 받은 뒤 최종 버튼을 누른다. 완료 화면과 관리 화면의 갱신 중단 표시를 확인해 결과를 반환한다.

첫 시연 단계는 5번에서 멈춘다. 실제 해지 실행은 다음 단계로 검증한다. 해지 사유가 필요하면 사용자가 선택하거나 미리 정한 답을 사용하며 에이전트가 사유를 지어내지 않는다.

## 6. 서비스별 절차와 MCP 도구 제안

서비스마다 다음 정보를 가진 절차 문서를 만든다.

| 항목 | 내용 |
| --- | --- |
| 지원 범위 | 서비스, 결제 경로, 앱 버전, OS, 언어, 검증 기기 |
| 진입 경로 | 관리 URL·딥링크, 패키지명, 필요 시 상품 ID |
| 화면 식별 | 예상 화면·요소의 ID, 텍스트, 설명과 계정 확인 방법 |
| 실행 절차 | 단계별 사전 조건, 클릭 대상, 다음 화면 조건 |
| 중단 조건 | 인증 요청, 대상 불일치, 알 수 없는 화면, 시간 초과 |
| 완료 근거 | 해지 완료 문구, 갱신 중단 상태, 이용 종료일 |
| 유지보수 | 절차 버전, 마지막 검증일, 현재 지원 여부 |

현재 `service fee modified.csv`의 해지 관리 URL은 진입 후보로 활용할 수 있다. URL이 존재한다는 이유만으로 자동 해지 지원으로 표시하지 않는다.

MCP 인터페이스는 아래와 같이 제안한다. 도구 이름과 데이터 형식은 구현 전 확정한다.

| 도구 예시 | 역할 |
| --- | --- |
| `prepare_cancellation` | 대상·결제 경로·지원 여부 확인 후 작업 생성 |
| `navigate_cancellation` | 승인된 연결 기기에서 해지 확인 화면까지 진행 |
| `execute_cancellation` | 해당 작업의 사용자 승인 검증 후 실행 |
| `get_cancellation_status` | 진행 상태, 사용자 개입 사유, 완료 근거 조회 |

기존 조회 토큰에 실행 권한을 추가하지 않는다. 기기 연결과 해지 실행 권한을 분리하고, 표시한 대상·행동에 묶인 짧은 유효기간의 일회성 승인을 검증한다. 계정·대상·해지 효과가 달라지면 승인을 다시 받는다. 범용 원격 셸이나 임의 좌표 클릭 도구를 외부 MCP에 공개하지 않는다.

작업 상태 예시:

```text
준비 → 화면 이동 → 사용자 확인 대기 → 실행 중 → 완료 검증
             ↘ 사용자 개입 필요 / 지원 불가 / 중단
실행 중·완료 검증 → 결과 불명 → 상태 재조회 또는 사용자 확인
```

동일 작업의 중복 실행을 막는다. 최종 클릭 후 연결이 끊겼다면 실패로 단정해 다시 누르지 않고 실제 구독 상태부터 확인한다. 클릭 성공만으로 해지 완료를 기록하지 않으며 확인할 수 없으면 ‘결과 불명’으로 남긴다.

## 7. 개인정보와 기존 기획의 변경 지점

기존 기획은 에이전트의 읽기 전용 접근과 외부 LLM 전송 항목을 가맹점명·금액·날짜로 제한한다. 자동 해지는 실행 권한과 화면 데이터 처리를 추가하므로 실제 도입 시 관련 원칙을 함께 개정해야 한다. 이 문서는 확장 검토안이며 기존 분석 MVP의 권한을 변경하지 않는다.

- 비밀번호·인증번호·세션 토큰을 MCP 응답이나 LLM 입력에 넣지 않는다.
- 화면 처리는 로컬의 필요한 요소 정보부터 사용한다. 원본 스크린샷의 상시 업로드·저장을 기본으로 하지 않는다.
- 외부 이미지 모델을 사용하면 전송 항목·목적을 별도로 설명하고 동의를 받는다. 계정·알림 등 불필요한 정보가 포함된 화면은 전송하지 않는다.
- 작업 기록에는 대상, 승인·실행 시각, 절차 버전, 결과와 필요한 최소 근거를 남긴다. 스크린샷을 저장하면 별도 보관 기간·삭제 기능을 정한다.
- 접근성 권한 허용, PC 디버깅 연결 승인, 개별 해지 실행 승인은 서로 다른 권한이다.

## 8. 단계별 개발과 검증 기준

| 단계 | 개발 내용 | 완료 기준 |
| --- | --- | --- |
| 1. 대상 조사 | 서비스 1~2개 선정, 결제 경로·링크·수동 절차 확인 | 지원 환경과 재현 가능한 절차 기록 |
| 2. 화면 이동 시연 | ADB + UI Automator 실행기, 필요 시 정적 분석 | 테스트 계정에서 해지 확인 화면 도달, 최종 클릭 없이 중단 |
| 3. 완료 시연 | 작업 승인, 최종 실행, 상태 확인, MCP 연결 | 팀이 관리하는 테스트 구독에서 갱신 중단 확인 |
| 4. 폰 독립 실행 검토 | 접근성 기반 고정 절차, 권한·개인정보 설계 | 지원 기기 재검증 및 배포 시점 정책 검토 |

단계 3은 테스트용 자체 구독 화면에서 먼저 검증할 수 있다. 발표에서 모의 환경임을 명시하고 외부 서비스 실제 해지 검증과 구분한다. 외부 서비스 완료 시연은 해지를 허용한 팀 테스트 구독에서 수행한다.

필수 확인 상황은 정상 진행, 잘못된 계정·대상, 이미 해지된 구독, 로그인·추가 인증, 앱 화면 변경, 연결 끊김, 중복 요청이다. 화면 도달률과 완료 검증률을 별도로 기록하고 지원하지 않는 경로를 성공으로 집계하지 않는다.

## 9. 다음 결정 사항

- [ ] 첫 지원 서비스와 결제 경로 1~2개 선정
- [ ] 테스트 기기·OS·앱 버전·언어 선정
- [ ] 해지 확인 화면 도달과 실제 해지 완료 중 발표 범위 결정
- [ ] 테스트 계정·구독 준비, 모의 환경 사용 여부 결정
- [ ] PC 연결형 이후 안드로이드 앱까지 개발할지 결정
- [ ] 실제 도입 시 기본 기획의 실행 권한·개인정보 원칙 개정

본문에 연결한 공식 문서는 작성일 기준 참고 자료다. 특정 서비스의 자동 해지 가능 여부는 해당 계정·결제 경로·앱 버전에서 직접 확인해야 한다.
